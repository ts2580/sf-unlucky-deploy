# 0.8.0 정식 릴리스 준비

사용자 요청: main 승격 PR 준비 및 마이너 버전 상향. `0.7.0`에서 `0.8.0`으로 변경하며, 태그 생성·GitHub Release 공개·npm 발행은 이후 단계.

## 대상과 현재 상태

| 대상 | 준비 내용 | 상태 |
| --- | --- | --- |
| 일반판 | `@trstyq/sf-unlucky-deploy@0.8.0` 및 CLI·두 잠금 파일 버전 일치 | `IMPLEMENTED_LOCAL` |
| 릴리스 노트 | `docs/releases/v0.8.0.md` | `IMPLEMENTED_LOCAL` |
| canary 반영 | [#53 npm tar 6 호환성](https://github.com/ts2580/sf-unlucky-deploy/pull/53), [#54 Git·Apex·비교 UI 및 버전 상향](https://github.com/ts2580/sf-unlucky-deploy/pull/54) | `PLANNED` |
| main 승격 | 기존 [canary → main PR #52](https://github.com/ts2580/sf-unlucky-deploy/pull/52)에 선행 PR 반영 후 검증 | `PLANNED` |
| 정식 발행 | 최신 main의 annotated tag `v0.8.0`, 일반판 `next` 발행 | `PLANNED` |
| Windows 번들 | `0.8.0-win32-x64.1` 생성·오프라인 검사·`win32-x64` 발행 | `PLANNED` |
| 기본 설치 채널 | 두 산출물 검증 후 `latest=0.8.0` 승격 | `PLANNED` |

준비용 파일이나 이전 버전의 CI·설치 검사 성공을 정식 `0.8.0` 배포 완료 증거로 사용하지 않음.
원격 CI 결과와 검사 대상 커밋은 각 PR에 기록하며, 선행 PR을 합친 canary/main에서도 해당 커밋의 검증 확인 필요.

## 준비 검증

로컬 준비 검사 통과: 버전·잠금 파일 동기화, npm 배포 정책 14개, CLI 7개, 루트 빌드.
준비용 tarball을 Linux Node 24.21.0에 설치하여 `sfud 0.8.0`, 홈 설정 자동 초기화·기존 설정 보존·UI 자산·정상 종료·SQLite 쓰기·다른 작업 디렉터리 재시작 검사 통과.

```bash
npm run release:check -- v0.8.0
npm run lockfile:check
npm run test:npm-policy
npx vitest run test/program.test.ts
npm run build
npx --yes npm@11.20.0 pack --ignore-scripts --pack-destination /tmp/sfud-v0.8.0-preparation
node scripts/package-smoke.mjs /tmp/sfud-v0.8.0-preparation/trstyq-sf-unlucky-deploy-0.8.0.tgz
```

출력 디렉터리는 미리 생성. 준비용 tarball은 로컬 설치 검사에 사용하며, 정식 발행에는 main 태그의 Release 워크플로에서 생성한 파일 사용.

## 병합 및 발행 순서

1. #53·#54의 필수 CI 성공 확인 후 사용자가 canary에 병합. 두 PR 반영 뒤 최신 canary 및 #52의 필수 검증 확인.
2. #52 head에 tar 6 수정이 포함된 것을 확인한 뒤 해당 리뷰 스레드 재검증·리솔브. 승격 PR 검토 완료 후 사용자가 main에 병합.
3. 발행 요청 후 최신 main SHA와 버전·잠금 파일·미사용 태그를 확인하고 annotated tag `v0.8.0` 생성·push.
4. GitHub Release의 전체 검사와 OS별 동일 tarball 설치 검사 완료 후 태그·커밋·manifest·SBOM·SHA256SUMS 대조.
5. 같은 태그의 `publish-npm.yml`로 검증된 일반판 파일을 `next`에 발행하고 registry 바이트·integrity 확인.
6. 일반판 산출물이 확정되면 `scripts/windows-bundle-policy.mjs`에 `0.8.0`, main 원본 SHA, 실제 tarball SHA-256, 번들 버전 `0.8.0-win32-x64.1` 고정. 현재 파일의 `0.7.0` 원본 고정 값은 이 단계까지 유지하며 해시를 추정해 넣지 않음.
7. Windows 번들 생성 및 Node 22.19/24의 빈 캐시·오프라인 설치·UI·정상 종료·SQLite·재시작 검사. 원본 앱·UI 바이트 일치 확인 후 같은 Release에 첨부하고 `win32-x64`에 발행.
8. 두 산출물의 GitHub·npm 파일 일치 확인 후 일반판 `latest` 승격. 최종 main SHA·태그·실행 URL·버전·채널·해시 보고.

PR 실제 병합은 저장소 정책에 따라 사용자가 수행. main 승격 진행·완료는 지정 Slack 채널에 보고.
실제 Salesforce Org 비교·검증·배포 결과는 자동 검사와 별도로 기록.
