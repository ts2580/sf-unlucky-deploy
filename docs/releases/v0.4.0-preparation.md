# 0.4.0 정식 릴리즈 준비

2026-10-04 사용자가 RC4의 업데이트 기능이 정상 작동함을 확인하고 `0.4.0` 정식 발행을 요청했다. 일반판·Windows 번들 발행과 검증 후 일반판 `latest` 승격을 진행한다. 이 문서는 준비 상태와 실행 순서를 기록하며, 준비 완료를 정식 배포 완료로 보지 않는다.

## 버전과 채널

| 대상 | 버전 | 공개 경로 |
| --- | --- | --- |
| 일반 npm 패키지 | `@trstyq/sf-unlucky-deploy@0.4.0` | 검증된 파일을 `next`에 발행한 뒤 승인 후 `latest` 승격 |
| SQLite 포함 Windows x64 | `@trstyq/sf-unlucky-deploy@0.4.0-win32-x64.1` | `win32-x64` |
| GitHub Release | `v0.4.0` | 사용자 병합 후 최신 `main`의 annotated tag, 정식 Release |

RC 번들 `0.4.0-rc.4.win32-x64.1`과 정식 번들 `0.4.0-win32-x64.1`을 구분한다. 둘 다 동일한 패키지 이름·CLI 명령을 사용한다. Windows 번들의 `sfud --version`은 원본 앱 버전을 표시한다.

## 준비 상태

- `IMPLEMENTED_LOCAL`: package.json·package-lock.json·npm-shrinkwrap.json·CLI 버전을 `0.4.0`으로 일치시킴.
- `IMPLEMENTED_LOCAL`: 정식 릴리즈 노트를 RC4의 기능·지원 Node·설정 전환 기준으로 갱신. 과거 버전의 테스트 수와 Org 배포 결과를 이번 버전의 검증 결과로 사용하지 않음.
- `IMPLEMENTED_LOCAL`: npm 발행 워크플로에서 태그 버전의 정확한 일반판 tarball만 선택. 같은 Release의 Windows 번들과 공존하도록 수정.
- `IMPLEMENTED_LOCAL`: Windows 설치 검사는 패키징 도구 checkout의 버전 대신 고정된 원본 앱 버전으로 CLI를 확인. 정식 버전 준비 중에도 RC4 원본 번들 검증 가능.
- `IMPLEMENTED_LOCAL`: `npm run release:check -- v0.4.0`, 잠금 파일 동기화, npm 배포 정책 12개·CLI 7개 테스트, 저장소 루트 `npm run build` 통과. 준비용 tarball을 Linux Node 24.20.0에서 설치하여 CLI·홈 설정·UI·SQLite 쓰기·다른 작업 디렉터리 재시작 검사 통과. 워크플로 YAML·Bash 구문과 diff 검사 통과.
- `VERIFIED_REMOTE`: 일반판과 Windows 파일이 함께 있는 실제 RC4 Release에서 일반판 파일 4개만 다운로드하고 원본 manifest·SHA256SUMS 검증 통과. 정식 npm OIDC 발행 실행 자체는 아직 미실행.
- `VERIFIED_REMOTE`: [RC4 Windows 번들 검사](https://github.com/ts2580/sf-unlucky-deploy/actions/runs/37172965307)에서 Node 22.19.0·24.21.0 오프라인 설치·CLI·UI·SQLite·다른 작업 디렉터리 재시작 통과. 이 결과는 RC4 기준이며 정식 tarball의 설치 검사는 별도 수행.
- `DEPLOYED`: RC4 일반판 `next=0.4.0-rc.4` 및 SQLite 포함 Windows `win32-x64=0.4.0-rc.4.win32-x64.1` npm 공개 확인. Windows registry 파일·검증된 아티팩트·GitHub 첨부 파일의 바이트 및 integrity 일치 확인. 일반판 `latest=0.4.0-rc.1` 유지.
- 사용자 실사용 확인: 2026-10-04 RC4 업데이트 기능 정상 작동 및 정식 발행 승인. 사용자가 수행한 확인이며 자동 검사 결과와 구분.
- `PLANNED`: 정식 준비 변경의 canary 반영, `canary → main` 승격, 정식 태그·일반판·Windows 번들 발행 및 `latest` 승격.

[PR #36](https://github.com/ts2580/sf-unlucky-deploy/pull/36)에 Windows 패키징·동시 발행 절차와 정식 준비 변경을 함께 반영한다. 필수 검증 성공 후 사용자가 canary에 병합하고, 이후 main 승격 PR을 진행한다.

준비용 tarball은 `working/releases/v0.4.0-preparation/`에 있으며, 최종 main의 Release 워크플로가 만드는 정식 발행 파일과 구분한다.

## 사용자 테스트에서 확인할 항목

- 실제 사용하는 로컬 또는 원격 개인용 환경의 로그인·로그아웃, 기존 설정과 Org 연결 유지
- Git 루트·하위 DX 프로젝트 선택과 등록 브랜치의 저장소·경로 표시
- 비루프백 HTTP를 사용하는 경우 dry-run 요청 시작 및 결과 조회
- 실제 대상 Org의 검증·배포와 결과 확인, 사용하는 경우 Quick Deploy
- 배포 설정 저장·불러오기, 새로고침 후 선택 복원·진행 작업 이어보기
- Windows 번들 설치 후 UI 시작, 기록 저장 및 재시작 후 조회

사용자는 업데이트 기능의 정상 작동을 확인했다. 추가로 발견한 문제는 수정 후 해당 경로를 다시 검증한다.

## 발행 순서

1. 사용자 테스트 결과를 기록하고 준비 변경의 빌드·버전·잠금 파일·배포 정책 검사를 완료한다. 작업 브랜치에서 canary 대상 PR을 만들고 필수 CI 성공 후 사용자가 병합한다. PR #36 반영도 확인한다.
2. canary 검증 후 `canary → main` PR을 만들고 필수 CI 성공 후 사용자가 병합한다. 저장소 정책에 따라 승격 진행·완료를 Slack에 보고한다. 에이전트는 PR 병합이나 자동 병합 설정을 실행하지 않는다.
3. 사용자 발행 승인 후 최신 원격 main SHA, 작업 트리, 버전 `0.4.0` 및 미사용 태그를 확인하고 해당 SHA에 annotated tag `v0.4.0`을 생성·push한다.
4. 해당 태그의 GitHub Release 워크플로가 전체 검증·설치 행렬을 통과했는지 확인한다. 공개된 일반 tarball·manifest·SBOM·SHA256SUMS와 태그·커밋을 대조한다.
5. `publish-npm.yml`을 `v0.4.0` ref와 동일 `release_tag`로 실행한다. 등록된 trusted publisher 사용 여부를 확인하며, 수동 CLI 발행 시에는 동일 검증 파일과 npm 브라우저 2단계 인증을 사용한다. `next`로 발행한 파일의 registry 바이트·integrity를 검증한다.
6. 일반 `0.4.0` 산출물이 확정된 뒤 Windows 정책에 원본 버전·main 소스 SHA·tarball SHA-256과 `0.4.0-win32-x64.1`을 고정한다. 준비 단계에는 RC4의 고정 값을 유지하며 정식 SHA·해시를 추정해 넣지 않는다.
7. Windows 워크플로의 생성·Node 22.19/24 오프라인 검사를 통과한 파일을 같은 `v0.4.0` Release에 추가하고 `win32-x64`로 발행한다. 원본 앱·UI 바이트, GitHub 첨부 파일, registry tarball 일치를 확인한다.
8. 두 패키지 검증 완료 및 사용자 승인 후 일반판 `latest`를 `0.4.0`으로 승격한다. 기본 설치와 Windows 태그가 각 버전을 가리키는지 확인하고 릴리즈 결과를 보고한다.

npm 발행 성공 또는 HTTP 202 접수 후 조회가 일시적으로 404여도 재발행하지 않는다. 원래 발행 결과를 보존하고 registry 조회·해시 검증만 재개한다.

## 완료 증거

- 정식 main SHA·annotated tag 및 성공한 Release 실행 URL
- 일반판과 Windows 각각의 버전·npm 태그·tarball SHA-256·registry integrity
- GitHub 첨부 파일과 npm 파일의 바이트 일치
- 정식 산출물의 OS별 설치 검사와 Windows 오프라인 검사
- 사용자 실사용 테스트 결과 및 미해결 문제 여부
- `latest=0.4.0`, `next=0.4.0`, `win32-x64=0.4.0-win32-x64.1` 최종 확인
