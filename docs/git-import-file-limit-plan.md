# Git 가져오기 파일 수 제한 변경안

상태: 아래 제안은 2026-09-21 사용자 요청에 따른 비교 제한 정책으로 대체되었다.

## 적용된 정책

- 설정 화면에서 사용자별 최대 비교 파일 수를 1~50,000개로 저장한다. 기본값은 2,000개다.
- 가져오기 단계의 기본 파일 수 제한을 제거했다. 파일당·전체 바이트, 저장 공간, 시간 제한은 유지한다.
- 비교에 사용할 메타데이터 파일의 상대 경로 합집합이 설정값을 초과하면 차이를 계산하지 않고 Source 목록만 반환한다.
- 비교하지 않은 항목은 `SOURCE`로 표시하며 선택 배포와 Dry-run은 계속 허용한다.
- 당시 파일 수·상한·초과 여부는 비교와 배포 이력에 보존한다.
- Git 추출은 이미 일괄 blob 확인과 독립 index를 사용하는 `git restore`로 전환했다.
- 아래 원인·권장 변경·검증 목록은 이전 설계 기록이며 현재 구현 설명이 아니다.


## 이전 제한과 원인

- `GitMaterializer.materialize()`는 타입 선택 이후의 파일 수를 센다. 저장소 전체 파일 수가 아니다.
- `CustomField`는 각 필드 파일과 부모 객체 설명 파일, 프로젝트 설정을 함께 가져오므로 2,000개를 쉽게 넘는다.
- `maximumFiles` 옵션은 존재하지만 `GitImportService`에서 관리자 설정으로 전달하지 않는다.
- 파일 수 외에도 추출 합계 100 MiB, 파일당 10 MiB, 수신 pack 100 MiB 한도가 있다.
- 사용자별 임시 저장 500 MiB, 서버 전체 2 GiB, 동시 가져오기 2개가 기본값이다.
- `GitObjectStore.readBlob()`는 파일마다 `git cat-file`을 실행한다. 부분 가져오기는 추가 존재 확인까지 실행한다.
- `ls-tree`와 일괄 존재 확인의 출력은 기본 4 MiB를 넘으면 실패한다. 파일 수만 올리면 큰 트리에서 다시 막힐 수 있다.

## 권장 변경

1. 파일 수 기본값을 **20,000개**로 바꾸고 `SFUD_GIT_MAX_FILES`로 설정하게 한다.
   초기 관리자 설정 범위는 1~50,000개로 제한하고, 환경값이 잘못되면 시작 시 설명과 함께 실패한다.
   20,000개는 성능을 검증할 목표값이며 현재 성능 보장은 아니다.
2. 파일당·전체 바이트 한도와 사용자·서버 저장 공간 한도는 유지한다.
   많은 작은 필드를 허용하는 변경과 큰 개별 파일을 허용하는 변경을 분리한다.
3. 파일 내용 읽기는 **지속 실행하는 `git cat-file --batch` 프로세스**로 묶는다.
   응답 헤더의 실제 크기를 검증한 뒤 파일별로 스트리밍하고, 취소·타임아웃·용량 초과 시 프로세스를 종료한다.
   기존 인증, 경로 검증, implicit lazy fetch 차단은 유지한다. 없는 blob의 네트워크 수신 묶음은 별도로 유지한다.
4. `ls-tree`는 NUL 구분 레코드를 스트리밍 해석하고 트리 항목 수·경로 길이·처리 시간에 별도 상한을 둔다.
   blob 존재 확인은 제한된 크기의 묶음으로 처리해 4 MiB 출력 한도에 걸리지 않게 한다.
5. 추출 전 선택 파일 수를 검사해 화면에 `선택 24,310개 / 허용 20,000개`처럼 원인을 표시한다.
   blob 크기는 확인되는 시점에 추가 검증한다. 현재의 포괄적인 용량 초과 오류만 보여주지 않는다.

## 적용 전 검증

- 설정 파일까지 포함한 19,999·20,000·20,001개 경계 테스트 및 관리자 설정 검증.
- 20,000개 필드를 사용하는 실제 로컬 Git fixture로 가져오기 시간, Git 프로세스 수, 최대 RSS 측정.
- 4 MiB를 넘는 트리와 한글 경로, 같은 blob을 공유하는 파일, 여러 package directory 검증.
- 작은 파일 다수, 단일 파일 10 MiB 초과, 합계 100 MiB 초과를 각각 검증.
- 동시 가져오기 2개, 중간 취소·실패 시 임시 파일/프로세스/저장 공간 회수 검증.
- 변환 후 CustomField 비교 결과와 화면 목록의 수·응답 크기 확인. 필요하면 결과 목록 페이지 처리도 별도 적용.

파일 수를 무제한으로 풀기보다 위 설정·읽기 방식·오류 표시를 함께 바꾸는 것을 권장한다.
