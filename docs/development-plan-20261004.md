# 개인용 배포 흐름 개선 개발 계획

작성일: 2026-10-04

한 명의 Salesforce 개발자가 설정부터 비교·검증·배포, 실패 후 복구까지 쉽게 끝내는 것을 목표로 한다. 리뷰에서 확인한 P1 한 건과 P2 두 건을 먼저 해결하고, 최초 설정 안내·배포 설정 저장·오류 해결 안내·배포 직전 확인·작업 이어보기의 다섯 개선을 단계적으로 진행한다.

초기 계획은 RC4 리뷰 수정을 먼저 발행한 뒤 개선 기능을 진행하는 순서였다. 계획 승인 후 GPT 6.1 Sol 작업자에게 구현을 분담하고, 주 에이전트가 코드와 실패 경계를 검토했다. 전체 구현·로컬 검증 후 사용자의 배포 요청에 따라 리뷰 수정과 다섯 개선을 이번 RC4에 함께 포함한다. 기능별 커밋은 분리하고, canary PR 검증·사용자 병합·Release 검증·npm 발행 순서를 따른다.

## 현재 상태와 적용 범위

| 항목 | 현재 상태 | 구현 및 남은 확인 |
|---|---|---|
| P1 원격 HTTP에서 배포 요청 UUID 생성 실패 | `IMPLEMENTED_LOCAL` | 수정 유지 및 최종 릴리즈 변경 집합에서 회귀 확인 |
| P2 하위 DX 프로젝트 가져오기와 브랜치 등록 실패 | `IMPLEMENTED_LOCAL` | 후보 탐색·선택, 실제 경로 보존과 커밋 재확인 구현 |
| P2 계정 별칭 때문에 서로 다른 저장소가 같은 이름으로 표시 | `IMPLEMENTED_LOCAL` | 계정 별칭과 저장소 경로 표시, 호스트·프로젝트 식별 정보 보존 |
| 최초 설정 안내와 환경 점검 | `IMPLEMENTED_LOCAL` | setup·doctor 구현, 실제 Windows ACL 검증은 남음 |
| 자주 쓰는 배포 설정 저장 | `IMPLEMENTED_LOCAL` | 사용자별 저장·불러오기·삭제, 소스·대상 재검증 구현 |
| 실패 원인과 수정할 곳 연결 | `IMPLEMENTED_LOCAL` | 구조화된 오류, 정제된 상세 복사, 설정 이동과 복귀 구현 |
| 배포 직전 내용 확인 | `IMPLEMENTED_LOCAL` | 확정 Git 소스·대상·범위·테스트 요약과 확인 절차 구현 |
| 화면을 닫아도 작업 이어보기 | `IMPLEMENTED_LOCAL` | 작업 URL 복원, 원래 제출 ID 조회·재시도, 탭 초안과 새 작업 설정 복사 구현 |

P1은 앞선 실행에서 관련 단위 테스트 6개, 브라우저 테스트 30개, 타입·품질·빌드 검사를 통과했다. 브라우저 검증은 실제 비루프백 HTTP Origin에서 진행했으며 Salesforce 응답은 모의 API를 사용했다. 이 결과는 외부 Org 배포나 npm 발행 증거가 아니다. `VERIFIED_REMOTE`와 `DEPLOYED`는 해당 원격 검증·반영 증거를 확보한 단계에만 사용한다.

작업 브랜치는 `feature/release-0.4.0-rc.4`이며 개인용 원격 접속, P1·P2 수정, 다섯 개선과 RC4 버전·릴리즈 노트를 포함한다. 현재 체크아웃을 유지하고 기능별 변경 범위를 구분한다.

## 구현 원칙

- 개인용 여부와 접속 주소를 분리한다. 루프백 개인용, 비밀번호로 보호하는 원격 개인용, 기존 사용자별 모드를 유지한다.
- `SFUD_TOKEN_SECRET`은 Git·Salesforce 인증 저장용 암호화 키, `SFUD_ACCESS_PASSWORD`는 앱 접속 비밀번호로 유지한다. 기존 키를 자동 교체하지 않는다.
- 기존 Git 탐색·경로 검증, 소유권 검사, Org identity 검사, payload 체크섬, 배포 승인과 중복 제출 방지를 재사용한다.
- 저장한 설정·화면 복원·오류 안내가 실제 배포를 자동 실행하지 않도록 한다. 검증 결과의 재사용은 기존 유효성 검사와 승인 절차를 따른다.
- 계정·권한 체계를 확대하지 않는다. 새로운 외부 서비스나 AI 오류 분석 서비스 도입은 이번 범위에 포함하지 않는다.
- 기존 데이터에 필요한 변경은 순차 마이그레이션으로 추가한다. 최초 설정이나 업그레이드로 기존 DB·키·사용자 설정을 초기화하지 않는다.

## 1단계 RC4 리뷰 수정

### P1 원격 HTTP 요청 UUID 생성

수정 위치: [DeploymentPage](../ui/src/deployment/DeploymentPage.tsx), [UUID 생성 함수](../ui/src/deployment/idempotency-key.ts), [HTTP 회귀 검사](../e2e/remote-http-deployment.spec.ts).

`crypto.randomUUID()`를 사용할 수 있으면 기존 API를 이용하고, 없는 환경에서는 `crypto.getRandomValues()`의 16바이트 난수로 UUID v4를 생성한다. dry-run과 직접 배포 모두 같은 생성 함수를 사용한다. 난수 생성 실패를 약한 난수나 시간 기반 ID로 대체하지 않는다.

이미 적용한 수정을 유지하면서 다음 완료 기준을 확인한다.

- 실제 Chromium의 비루프백 HTTP Origin에서 `isSecureContext=false`, `crypto.randomUUID` 부재를 확인한다. 브라우저 API를 강제로 삭제하거나 Origin을 보안 컨텍스트로 취급하는 옵션으로 대체하지 않는다.
- 두 POST 요청 모두 올바른 UUID v4와 기존 CSRF 토큰을 전송한다.
- 결과를 확인하지 못해 재시도하는 동안 동일 작업의 idempotency key를 유지한다. 새 작업과 기존 작업 재시도를 구분한다.
- 기존 HTTPS·루프백 경로와 검증 후 승인 배포 흐름을 유지한다.

### P2 DX 프로젝트 경로 자동 탐색과 선택

리뷰 당시 [GitImportDialog](../ui/src/git/GitImportDialog.tsx)는 일반 가져오기와 브랜치 등록에 `projectRoot: '.'`을 고정해서 전송한다. [GitImportService](../src/git/git-import-service.ts)는 경로가 없으면 후보를 탐색하고, 하나일 때 자동 진행하며 여러 개면 `SELECTING`으로 전환한다. [GitRegistrationService](../src/git/git-registration-service.ts)는 별도로 생략된 경로를 `'.'`으로 저장하므로 UI 상수만 제거해서는 등록 문제가 해결되지 않는다.

일반 가져오기는 다음과 같이 수정한다.

1. 사용자가 경로를 명시적으로 선택하지 않았다면 `projectRoot`를 생략한다.
2. 유효한 프로젝트가 루트 하나이면 루트로, 하위 폴더 하나이면 그 폴더로 자동 진행한다.
3. 후보가 여러 개면 기존 `SELECTING`과 [GitProjectList](../ui/src/git/GitProjectList.tsx)의 선택 API를 유지한다. `'.'` 후보는 먼저 제시하되, 다른 프로젝트를 선택할 수 있게 한다.
4. 루트 후보가 없는 저장소에 `'.'`을 대신 넣지 않는다. 프로젝트가 전혀 없으면 기존 `DX_PROJECT_NOT_FOUND` 안내를 표시한다.

브랜치 등록에는 고정할 프로젝트 경로를 확인하는 절차를 추가한다.

- 기존 인증·Git 캐시·`GitMaterializer.discover()`를 재사용하는 프로젝트 후보 조회를 만든다. 제안 API는 `POST /api/v1/git/project-roots`이며, 연결·저장소·ref·예상 커밋 SHA를 받아 정규화된 후보 경로와 확인한 커밋을 반환한다.
- 후보가 하나이면 바로 선택하고, 여러 개면 등록 모달에서 실제 경로를 고른 뒤 등록한다. 경로를 모르는 사용자도 직접 입력 없이 선택할 수 있어야 한다.
- 저장소·브랜치·연결·커밋이 바뀌면 이전 후보와 선택을 폐기한다. 서버도 등록 시 선택한 경로와 커밋을 재검증한다. ref가 이동했으면 다시 확인하도록 안내한다.
- 새 UI는 확인한 실제 경로를 등록 요청에 포함한다. 서버에서 누락된 경로를 계속 지원해야 한다면, 후보가 하나일 때만 해결하고 여러 개일 때는 `PROJECT_SELECTION_REQUIRED`로 처리한다. 무조건 `'.'`을 저장하는 기본값은 제거한다.
- 이후 브랜치 동기화·비교에도 저장한 프로젝트 경로를 적용한다. 경로가 삭제되었으면 다른 프로젝트로 자동 전환하지 않는다.
- 기존 명시적 `'.'` 등록은 유지한다. 과거 잘못 등록된 경로는 사용자에게 수정·재등록을 안내하고 임의로 바꾸지 않는다.

후보 탐색은 허용된 저장소의 Git 트리에 한정한다. 서버 파일 시스템 전체 탐색 기능을 만들지 않는다. 기존 소유자 검사, 캐시 격리, 시간·용량 한도, 경로 탈출·심볼릭 링크 방어를 유지한다.

검증 대상은 루트 하나, 하위 프로젝트 하나, 하위 프로젝트 여러 개, 루트와 하위 프로젝트 공존, 프로젝트 없음, 존재하지 않는 지정 경로다. 실제 서비스 fixture로 일반 가져오기와 등록→동기화→비교까지 확인하고, 브라우저에서 후보 선택·브랜치 변경 시 선택 초기화를 확인한다. 관련 검사: `test/git-import-service.test.ts`, `test/git-registration-api.test.ts`, `e2e/git-import.spec.ts`.

### P2 별칭과 저장소 식별 정보 보존

리뷰 당시 `GitRegistrationService.sources()`는 연결 별칭으로 저장소 경로를 대체한다. 계정 범위 연결 하나로 여러 저장소의 같은 브랜치를 등록하면 label과 detail이 모두 같아질 수 있다.

표시 규칙을 다음과 같이 정한다.

| 연결 또는 등록 형태 | 주 표시 예시 | 항상 보존할 보조 정보 |
|---|---|---|
| 계정 범위 연결 | `업무 계정 · team/billing · main` | Git 호스트와 전체 저장소 경로, 프로젝트 경로 |
| 같은 계정의 다른 저장소 | `업무 계정 · team/inventory · main` | 위 저장소와 구별되는 전체 경로 |
| 저장소 전용 연결 | `결제 서비스 · main` | 실제 저장소 경로와 프로젝트 경로 |
| 등록 항목에 개별 별칭 지정 | `결제 운영 반영 · main` | 별칭과 무관하게 실제 호스트·저장소·프로젝트 경로 |

- 연결 조회에 연결 범위를 판별할 저장소 정보를 포함한다. 별칭은 표시 이름으로만 쓰고 실제 source ID와 저장소 identity는 유지한다.
- [WorkspaceSource 계약](../src/api/workspace-contracts.ts)의 `detail`과 선택 UI에 식별 정보를 전달한다. 별칭이 같아도 보이는 화면과 키보드 선택에서 구분할 수 있어야 한다. 툴팁만으로 구별하게 만들지 않는다.
- 같은 이름의 저장소가 다른 호스트에 있거나, 한 저장소의 같은 브랜치에 프로젝트가 여러 개 있는 경우도 구분한다.
- 표시할 URL은 인증정보·쿼리·토큰을 제외한 정규화된 저장소 주소를 사용한다.

완료 기준은 `team/billing`과 `team/inventory`의 `main`, 동일 basename의 다른 namespace·호스트, 같은 저장소의 다른 프로젝트 경로, 별칭 변경·제거, 타 사용자 연결 격리에 대한 서비스·API·브라우저 검사 통과다.

## 2단계 처음 쓰기와 반복 작업 단순화

### 최초 설정 안내와 환경 점검

기존 `config init`과 [홈 설정 로더](../src/config/user-config.ts)를 기반으로 대화형 `sfud setup`과 읽기 전용 `sfud doctor`를 추가하는 안을 채택한다. 사용자가 직접 서버 터미널에서 설정한다. 공개된 미인증 웹 화면에서 최초 접속 비밀번호를 선점할 수 있는 흐름은 만들지 않는다.

`sfud setup`의 첫 선택은 다음 두 가지다.

- 내 PC에서만 사용: `LOCAL=true`, 루프백 주소, 접속 비밀번호 선택 사항.
- 원격 서버에서 혼자 사용: `LOCAL=true`, 수신 주소, 접속 비밀번호 필수. 공개 URL과 신뢰 프록시는 프록시를 사용하는 경우에만 추가 입력.

기존 사용자별 서버 설정은 보존하고 기존 운영 문서로 연결한다. 이번 안내에 새로운 팀 관리 흐름을 추가하지 않는다.

설정 저장 전 적용할 파일·모드·주소를 비밀값 없이 표시한다. 환경변수와 시작 스크립트가 홈 설정을 덮어쓰는 경우 실제 적용 우선순위를 안내한다. 개인용과 사용자별 DB를 전환하지 않고 필요한 경우 별도 저장 경로를 고르게 한다.

비밀번호는 숨김 입력과 재입력으로 확인한다. 기존 `SFUD_TOKEN_SECRET` 또는 호환 키가 있으면 그대로 사용한다. 키가 없고 기존 암호화 데이터도 없는 초기 설정에서만 생성·저장을 제안한다. 기존 암호화 데이터가 있는데 키를 읽을 수 없는 상황은 복구 안내로 처리하며 새 키를 생성하지 않는다. POSIX 파일 권한과 Windows ACL, 안전한 파일 교체·실패 복구 규칙을 유지한다.

`sfud doctor`는 다음 결과를 비밀값 없이 요약한다.

- Node·Git·Salesforce CLI 설치 여부와 지원 버전.
- 적용 중인 설정 파일·실행 모드·수신 주소와 프록시 설정의 형식·정합성.
- 비밀 설정의 존재·형식·파일 권한, 데이터 디렉터리 접근 상태.
- 구성으로 계산한 접속 URL과 실제 도달 여부를 구분한 안내. 프록시 뒤의 브라우저 접근 성공을 추정하지 않는다.
- 새 Salesforce 브라우저 OAuth 연결에 필요한 콜백 주소·포트 안내.

점검은 Org 변경이나 실제 배포를 수행하지 않는다. 비대화형 환경에서 `setup`은 입력을 기다리지 않고 필요한 설정과 실행 방법을 안내한다. `doctor`는 자동화에서 사용할 종료 코드와 선택적 JSON 출력을 제공한다.

완료 기준: 새 설치와 기존 설치, 기존 키 보존, 빈 환경변수 우선, 개인용·사용자별 DB 분리, 비밀값 비출력, 잘못된 프록시 설정, 비대화형 종료 및 Windows 실제 ACL 검사 통과. 설치 tarball에서 다른 작업 디렉터리로 실행한 결과도 확인한다.

### 자주 쓰는 배포 설정 저장

“개발 서버 반영”처럼 이름을 붙여 Source·Target·비교 범위·테스트 설정을 저장하고 불러오는 기능을 만든다. 저장 설정과 실행 결과를 구분한다.

저장할 값은 이름, 연결 또는 등록 브랜치 참조, 저장소·ref·프로젝트 경로, 허용된 서버 프로젝트 참조, 대상 Org의 안정적인 identity, 메타데이터 범위, 제외 패키지 선택, 테스트 수준·선택 클래스다. 자동 선택과 명시적 선택도 구분한다.

토큰·비밀번호·OS 임시 경로·만료되는 Git import ID·기존 dry-run 승인·이전 idempotency key는 저장 설정에 포함하지 않는다. 초기 버전에서는 컴포넌트 체크 목록까지 장기 저장하지 않고, 현재 비교 결과에서 다시 선택하게 한다.

- 제안 저장소: `deployment_presets` 테이블. 소유자, 이름, 설정 스키마 버전, 검증된 설정 JSON, 생성·수정 시각을 저장한다.
- 제안 API: 사용자별 목록·생성·수정·삭제와 설정 해석 API. 기존 인증·CSRF·역할 검사를 재사용한다. 이름·설정 크기·개수의 상한을 둔다.
- UI: 비교 및 배포 화면에 저장·불러오기 제공. 전체 흐름을 대체하는 별도 대시보드는 만들지 않는다.
- 불러오면 현재 연결·저장소·프로젝트·Org identity·권한을 재확인한다. 삭제·재연결·별칭 대상 변경·브랜치 이동을 알리고, 자동으로 비슷한 이름의 다른 대상으로 치환하지 않는다.
- 현재 소스로 다시 비교·검증한다. 불러오기만으로 dry-run 또는 실제 배포를 시작하지 않는다.

구현 위치는 새 공유 계약·저장소·라우트와 `DeploymentPage` 주변으로 제한한다. 아래 작업 이어보기와 공유할 수 있도록 선택 상태의 해석·검증 함수를 분리하되, 범용 워크플로 엔진으로 확장하지 않는다.

완료 기준: 같은 사용자 재로그인·재시작 후 저장 설정 유지, 타 사용자 접근 거부, 삭제된 연결·프로젝트 처리, 같은 Org 별칭의 대상 변경 차단, 가져오기 만료 후 재해석, 실제 배포 자동 제출 없음, 기본 비교·배포 흐름 회귀 통과.

## 3단계 확인과 복구 경험 개선

### 실패 원인에서 수정할 곳으로 연결

[DeploymentStatus](../ui/src/deployment/DeploymentStatus.tsx)의 기존 구조화된 Salesforce 진단과 서버 오류 코드를 확장한다. 초기 범위는 인증 만료, 연결·프로젝트 경로 오류, 메타데이터 의존성 누락, Apex 테스트·커버리지 실패, 원격 결과 재확인 필요 상태다.

- 요약 원인, 해당 컴포넌트·파일·클래스·메서드·줄 번호, 다음 조치를 한 묶음으로 표시한다.
- 확정된 사실과 가능한 해결 제안을 구분한다. 원문 메시지만 보고 누락된 의존성을 확정하거나 자동으로 배포 목록에 추가하지 않는다.
- 인증 만료는 해당 연결 설정으로, 프로젝트 오류는 해당 저장소·프로젝트 선택으로 이동한다. 돌아왔을 때 선택 상태를 보존한다.
- 제출 여부가 불확실하면 기존 `RECONCILE_REQUIRED` 확인으로 안내한다. 새 배포 버튼으로 우회시키지 않는다.
- 정제된 상세 오류 복사 기능을 제공하고 토큰·Auth URL·민감한 서버 경로를 제외한다. 분류되지 않은 오류도 기존 상세 정보를 볼 수 있게 한다.

완료 기준: 오류 fixture별 안내 정확성, 잘못된 확정 진단 없음, 민감정보 비노출, 재연결 후 선택 복귀, 미확정 작업 중복 제출 없음, 긴 오류와 모바일 표시 검사 통과.

### 배포 직전 내용 확인

비교·검증 결과를 이용해 Source와 Target, 실제 반영 범위를 한곳에 보여준다. 기존 승인·검증 장치를 이 요약으로 대체하지 않는다.

- Git Source는 호스트·저장소·브랜치 또는 태그·고정된 커밋·프로젝트 경로를 표시한다. 별칭만으로 실제 대상을 표시하지 않는다.
- Org는 별칭·사용자명·마스킹한 Org ID를 표시한다. 운영·샌드박스 표시는 서버가 확인한 정보로 판단하며 이름·도메인·edition만으로 추측하지 않는다. 확인할 수 없으면 “환경 확인 필요”로 표시한다.
- 선택 컴포넌트 수·타입, 테스트 수준·선택 테스트, 마지막 검증 상태를 표시한다. 검증된 payload가 있으면 그 checksum과 연결한다.
- 검증 후 배포와 직접 배포를 명확히 표시한다. 실제 배포 제출 직전에 최신 요약을 확인하게 하고, 운영 Org 여부와 대상 identity를 눈에 띄게 보여준다.
- 선택·커밋·대상 연결이 바뀌면 기존 확인 상태를 해제한다. 서버의 identity·generation·payload 검사와 기존 승인 조건을 유지한다.

완료 기준: 같은 별칭의 다른 Org 구분, 루트가 다른 동일 저장소 구분, 운영·샌드박스·미확인 표시, 선택 변경 후 재확인, 직접 배포·검증 후 배포 두 경로, 좁은 화면에서 긴 경로 확인 가능.

### 화면을 닫아도 작업 이어보기

서버에 존재하는 작업을 다시 조회하는 기능과 새 작업의 선택 상태 복원을 분리한다. [App](../ui/src/App.tsx)의 실행 기록과 `DeploymentPage`, `useWorkflowUpdates`를 연결한다.

- 실행 기록에서 작업 ID가 포함된 상세 URL로 이동한다. URL에는 작업 ID만 넣고 인증정보를 넣지 않는다.
- 로그인 후 서버에서 접근 가능한 작업을 GET으로 복원하고 SSE·polling을 다시 연결한다. 새로고침·재접속 자체로 POST를 보내지 않는다.
- 진행 중·완료·실패·재확인 필요 상태는 서버 값을 기준으로 표시한다. 여러 작업이 있으면 선택 목록을 제공하고 임의로 마지막 작업을 실제 배포 대상으로 지정하지 않는다.
- “이 설정으로 새 작업”은 2단계의 설정 해석·재검증을 재사용한다. 이전 승인과 checksum을 새 선택에 붙이지 않는다. 기존 검증의 배포 승인은 원래 작업을 열었을 때 기존 검사에 따라 처리한다.
- 작업 ID를 받기 전에 연결이 끊긴 경우가 별도 경계다. 사용자별 대기 요청에 원래 idempotency key와 요청 지문을 보존하고, 인증된 조회로 작업 생성 여부를 확인할 수 있게 한다. 결과가 불확실한 동안 새 키로 자동 재제출하지 않는다.
- 선택 초안은 세션 토큰을 포함하지 않는 사용자 소유 데이터로 저장한다. 만료 시간·개수 제한을 두고 탭별 초안을 구분한다. 실제 서버 작업 기록은 초안 정리와 무관하게 기존 보존 정책을 따른다.
- 다른 사용자의 작업 ID, 만료된 artifact, 삭제된 Git import는 접근 실패·만료 상태로 안내한다. 자동 재다운로드나 재배포로 숨기지 않는다.

완료 기준: 요청 전·요청 응답 전·큐 대기·실행 중·완료 후 각각의 새로고침과 브라우저 재접속, 서버 재시작, 타 사용자 ID 입력, 여러 탭, artifact 만료에서 작업 상태가 일관되고 중복 제출이 발생하지 않을 것.

## 작업 분리와 진행 순서

| 순서 | 변경 묶음 | 선행 조건 | 완료 후 판단 |
|---|---|---|---|
| 1 | P1 수정 유지와 P2 프로젝트 탐색 복원 | 현재 리뷰 재현 자료 | 일반 가져오기·등록·비교 회귀 확인 |
| 2 | P2 별칭과 저장소 식별 개선 | 프로젝트 경로 표시 규칙 | RC4 리뷰 수정 범위 확정 |
| 3 | RC4 전체 검증과 릴리즈 절차 | 리뷰 수정 완료 | canary 대상 PR 검증 및 사용자 병합 |
| 4 | 최초 설정 안내와 doctor | RC4 변경 기준 정리 | 실제 새 설치에서 설정 부담 확인 |
| 5 | 배포 설정 저장 | 안정적인 저장소·프로젝트·Org 식별 | 반복 작업에서 입력 감소 확인 |

| 7 | 작업 이어보기 | 선택 상태 해석과 작업 조회·권한 계약 | 재접속과 미확정 제출 경계 검증 |

위 표는 최초 구현 순서다. 각 기능은 검토 가능한 커밋으로 분리하며, 초기 설정·저장 설정·작업 복원의 계약과 검증을 각각 확인했다. 최종 배포 요청으로 이미 구현한 전체 범위를 RC4에 포함하므로, 전체 변경에 대한 PR 검증을 발행의 선행 조건으로 삼는다.

## 공통 검증과 릴리즈 완료 기준

1. 위험 경계를 재현하는 서비스·API 검사를 먼저 추가한다. 기존 동작을 그대로 따라 쓰는 검사는 늘리지 않는다.
2. `npm run typecheck`, `npm run quality`, 필요한 Vitest·Playwright 검사를 통과한다. 릴리즈 후보의 최종 변경 집합에서 전체 검증을 수행한다.
3. UI 변경은 루프백 HTTP, 실제 비루프백 HTTP, HTTPS 프록시 시나리오를 구분한다. PC·태블릿·모바일에서 입력·선택·오류·재시도·키보드 조작과 console/page error를 확인한다.
4. 코드 변경 후 저장소 루트에서 `npm run build`를 수행한다. 실행 중인 서버에 반영할 때는 올바른 프로세스를 재시작하고 제공되는 UI 자산이 새 빌드와 일치하는지 확인한다.
5. 설치·설정 기능은 Linux와 Windows의 실제 환경 및 최소 지원 Node에서 확인한다. Linux fixture 결과를 Windows ACL 검증으로 보고하지 않는다.
6. 버전·잠금 파일·릴리즈 노트·tarball 검사를 수행하고, 설치 후 CLI·UI·SQLite·재시작을 확인한다. Salesforce 모의 응답 검증과 실제 Org 작업 증거를 구분한다.
7. 변경은 작업 브랜치에서 PR을 통해 `canary`로 보낸다. 에이전트는 검증·PR 준비까지만 수행하며 병합은 사용자가 진행한다. RC는 최신 `canary`의 annotated tag와 기존 Release 검증 절차를 따른다.
8. GitHub Release 생성, npm 발행 응답, registry 산출물 확인을 각각 보고한다. 새 개선 기능의 계획 수립 자체를 구현·발행 승인으로 확대하지 않는다.

계획 승인에 따른 로컬 구현·검증 단계에서는 기존 사용자 설정·실제 Org 변경과 커밋·푸시·발행을 수행하지 않았다. 이후 배포 요청에 따라 작업 브랜치 커밋·푸시와 canary PR 준비를 진행한다. 사용자 병합 전 RC 태그·npm 발행을 수행하지 않는다.


## 구현 검토 기록

구현은 GPT 6.1 Sol 작업자에게 Git·오류 안내, 최초 설정, 저장 설정·복구로 나누어 맡겼고 주 에이전트가 통합 검토했다. 공통 저장소에서 기존 변경을 보존했으며 별도 worktree·커밋·푸시·릴리즈는 만들지 않았다.

중간 검토에서 다음 실패 경계를 보완했다.

- 요청 응답을 잃은 후 같은 별칭이 다른 Org를 가리켜도 원래 요청을 다른 Org에 제출하지 않는다. Source·Target identity 지문을 요청에 묶고 서버에서 재확인한다. 이미 생성된 작업의 동일 제출 ID 조회는 유지한다.
- 불명확한 최초 요청 뒤 재시도가 거부되어도 이전 제출 ID를 지우지 않는다. 요청의 최초 거부와 과거 제출 여부를 구분한다.
- 초안 저장의 수신 순서를 DB revision으로 보존한다. 기본값 자동 저장, 오래된 응답, 복제된 탭이 최신 선택을 덮어쓰지 않도록 했다.
- 서버 저장 전 새로고침과 BroadcastChannel 미지원 환경에서도 사용자별 임시 초안을 명시적으로 복원한다. 연결 오류로 초안 저장이 실패해도 설정 화면으로 이동할 수 있다.
- 등록 Git의 배포 확인에는 비교에서 확정한 커밋·프로젝트 경로를 사용한다. 초기 메타데이터 조회와 복원 응답 사이의 경쟁, 선택 목록 중복도 브라우저 검사로 수정했다.
- 기존 비밀 파일의 원문을 보존하고 두 설정 파일 교체 실패를 복구한다. 외부 파일 변경으로 복구할 수 없을 때 원본 백업까지 삭제하지 않는다.

현재 검증은 로컬 구현 증거다. 실제 Windows ACL 실행, 최소 지원 Node 실행, 이번 변경의 외부 HTTPS 프록시·실제 Salesforce Org 검증 및 발행은 별도 확인이 필요하다. 브라우저의 Salesforce/Git 응답은 fixture를 사용하며, 비루프백 HTTP의 보안 컨텍스트 제한은 실제 Chromium에서 검사했다.
